# K10 两地天气来信装置 / Two-city Weather Letter

## 1. 工程入口与保留模块

Arduino 工程入口：

```text
WeatherStory_TinySelector_K10/WeatherStory_TinySelector_K10.ino
```

目标板：`unihiker k10`，FQBN：`UNIHIKER:esp32:k10`。

本版本保留并继续使用：

- `FeatureExtractor.*`：固定 14 维输入特征；
- `StoryMoodModel.*` 与原 `model.h`：ArduTFLite 推理，固定 4 个 mood 输出；
- `StorySelector.*`：模型不可用或推理失败时的规则回退；
- `PersonalityLearning.*`：天气驱动的缓慢人格变化；
- `PersonalityMemory.*`：Preferences/NVS 跨重启保存；
- `StoryGenerator.*`、`StoryVocab.*`、`StoryControl.h`：故事模板和词库。

本轮没有重新训练模型，没有替换 `model.h`，也没有加入 LED、RGB 灯带或灯光效果。

## 2. 集中配置

所有现场常改参数都位于主程序顶部的 `Central configuration`：

```cpp
const char* WIFI_SSID = "enter Wifi";
const char* WIFI_PASSWORD = "enter password";

const CityConfig CITY_A = {"上海", 31.2304f, 121.4737f};
const CityConfig CITY_B = {"台中", 24.1477f, 120.6736f};

const bool DEMO_MODE = false;
const unsigned long WEATHER_REFRESH_INTERVAL_MS = 10UL * 60UL * 1000UL;
const unsigned long DEMO_REFRESH_INTERVAL_MS = 30UL * 1000UL;
```

不要提交真实 Wi-Fi 密码。本工程继续使用不需要 API Key 的 Open-Meteo。

## 3. 两地天气与 TinyML 兼容策略

程序按顺序请求上海和台中，各自保存在独立缓存中。单个城市失败时不会覆盖该城市上一次成功数据，也不会删除另一城市数据或上一封来信。只有本轮两个城市都成功时，才按真实天气产生新来信；演示模式可以使用两份缓存重新生成。

Open-Meteo 字段保持为：

```text
temperature_2m
relative_humidity_2m
precipitation
rain
weather_code
wind_speed_10m
is_day
```

送入原 14 输入 TinyML 模型前，两地数据合成为一个 `WeatherData`：

- 温度：两地平均；
- 湿度：两地平均并四舍五入；
- precipitation、rain、风速：两地较大值；
- rainy、snowy、stormy、cloudy、windy 标签：两地逻辑 OR；
- weatherCode：选天气严重等级更高的一地；
- isDay 和时间：使用收信地城市 B（台中）。

这只改变模型前的输入合成，不改变模型张量：仍为 14 输入、4 输出。

## 4. 来信定义与触发

`Letter.h` 定义：

```cpp
struct Letter {
  String fromCity;
  String toCity;
  String title;
  String body;
  String id;
  bool unread;
};
```

来信正文包含 From、To、两地天气摘要、TinyML/规则选出的 mood 和现有 StoryGenerator 生成的故事。ID 使用两地更新时间、关键天气字段、正文的 FNV-1a 哈希。只有 ID 与上一封不同才进入 `NEW_LETTER` 并触发一次电机；屏幕轮播和正文翻页不会触发电机。

## 5. 屏幕状态与分页

已检查本机安装的 `unihiker_k10` 1.0.0 源码：`initScreen()` 仅在方向 1 或 3 时注册 320×240 画布，方向 0 或 2 注册 240×320 画布。本工程最终使用：

```cpp
constexpr uint8_t SCREEN_DIRECTION = 1;
constexpr int SCREEN_WIDTH = 320;
constexpr int SCREEN_HEIGHT = 240;
```

方向 1 与方向 3 都是真横屏且互相倒置；本工程选择方向 1。安装约定为：从原本方向 2 的竖屏正向看，将 K10 顺时针转为横屏，原机身上边缘位于阅读者右侧，USB 线从右侧引出，机器运动时屏幕上边缘朝机器结构定义的“上方”。该朝向由库旋转关系确定，但仍必须在上传后目视确认文字没有上下颠倒；如果实际安装把 USB 放在左侧，应改用方向 3，不能交换坐标伪装旋转。

横屏统一布局为左右边距 10 px、顶部标题栏 34 px、正文从 y=40 到 y=218、底部状态栏 22 px。各状态独立绘制：

- `STARTUP`：居中显示初始化状态；
- `WAITING`：两地城市分列左右，中间是虚线和信封轮廓；
- `NEW_LETTER`：左侧约 65% 显示 From、To 和一行两地温度，右侧显示信封、mood 与 MOVING/READY；
- `READING`：页眉包含标题、From→To、页码，正文不会进入页脚；
- `ERROR / OFFLINE`：只显示错误类型和缓存状态，HTTP 细节仅写串口。

正文使用 K10 字体芯片的 `ASCII_GetInterval(..., ASCII_12_A)` 测量 16 px 英文字形推进宽度，中文按库源码规定的 12 px 推进宽度计算；英文优先在空格处断行，长单词可在 UTF-8 字符边界断开。正文区域按高度计算为每页 8 行，最多缓存 3 页；超长正文限制为 1400 字节，最后一页以省略号结束。分页只在接受新来信时计算一次，翻页只切换缓存页码。

代码层面可确认方向 1 会创建 320×240 画布；屏幕实际朝向、中文外观、USB 出线是否符合整机安装仍属于真机目视验收，编译成功不能替代这些检查。

Button B：阅读状态手动翻到下一页；离线状态读取缓存来信。

## 6. 正常模式与演示模式

正常模式：

```cpp
const bool DEMO_MODE = false;
```

每 10 分钟请求真实天气；失败后 1 分钟重试。Wi-Fi 与 HTTP 都有有限超时，不会无限等待。

演示模式：

```cpp
const bool DEMO_MODE = true;
```

成功取得两地缓存后：

- 按 K10 Button A：立即用缓存生成一封带新 demo nonce 的演示来信；
- 或每 30 秒自动产生一封演示来信；
- Button B 只翻页，不触发电机通知。

串口输入 `d` 也可请求演示来信；输入 `r` 重置人格 Preferences。

## 7. K10 与 L298N 最终接线

K10 边缘只有 P0、P1、I²C、BAT IN 四组接口。由于 L298N 的 MOTOR-A、MOTOR-B 排针已经焊好且不能并联，本工程把 I²C 组内的 SDA、SCL 临时改作普通数字输出，正好提供四根独立方向信号线。两台 N20 分别使用 A、B 通道，不需要分叉线。

| K10 边缘脚 | L298N | 程序常量 | 用途 |
|---|---|---|---|
| P0 | IN1 | `LEFT_MOTOR_IN1 = P0` | MOTOR-A 方向 1 |
| P1 | IN2 | `LEFT_MOTOR_IN2 = P1` | MOTOR-A 方向 2 |
| I²C SDA | IN3 | `RIGHT_MOTOR_IN3 = SDA` | MOTOR-B 方向 1 |
| I²C SCL | IN4 | `RIGHT_MOTOR_IN4 = SCL` | MOTOR-B 方向 2 |
| GND | GND | — | 必须共地 |
| BAT IN | 不接 | — | 不能作为电机驱动信号或电机电源输出 |

电机与电源接线：

- 左侧 N20 的两根线分别接 L298N `MOTOR-A` 两个排针；
- 右侧 N20 的两根线分别接 L298N `MOTOR-B` 两个排针；
- L298N `VMOTOR/+12V` 和 GND 接适合 N20 额定电压的独立电机电源；
- K10 GND、L298N GND、独立电机电源负极必须共地；
- 严禁用 K10 GPIO 或 K10 3.3V 给电机供电；
- 若模块另有 ENA/ENB 跳帽，两个跳帽都保持常开，不连接 PWM；
- 若某侧车轮方向相反，调整 `LEFT_MOTOR_REVERSED` 或 `RIGHT_MOTOR_REVERSED`，不要改业务逻辑。

重要：SDA/SCL 改作电机输出后，不能再接任何外部 I²C 模块。本程序也不能调用标准 `k10.begin()`，因为它会启动持续访问 I²C 的姿态后台任务；当前代码使用最小化初始化，只保留屏幕、按键、字体和板载 IO，因此板载光线、温湿度、加速度/姿态功能不可用。天气仍来自 Open-Meteo，不受影响。

## 8. 非阻塞电机状态机

`MotorController.*` 使用 `millis()`，不在动作中调用长 `delay()`：

```text
stop 100 ms
-> forward 450 ms
-> stop 150 ms
-> backward 450 ms
-> stop 150 ms
-> 重复共 2 次
-> final stop
```

开机、联网、天气请求、错误和重新初始化时都会 `stop()`。只有接受不同 ID 的新来信时调用一次 `triggerNewLetterMotion()`。

## 9. Arduino 依赖、编译和上传

依赖：

- UNIHIKER K10 board package（包含 `unihiker_k10`）；
- ArduinoJson；
- ArduTFLite；
- Chirale TensorFlow Lite 依赖；
- ESP32 自带 WiFi、HTTPClient、WiFiClientSecure、Preferences。

命令行干净编译：

```powershell
arduino-cli compile --fqbn UNIHIKER:esp32:k10 --build-path hardware/复制20260714k10/.arduino-build-k10 hardware/复制20260714k10/WeatherStory_TinySelector_K10
```

编译后必须同时确认完整应用文件存在：

```text
WeatherStory_TinySelector_K10.ino.elf
WeatherStory_TinySelector_K10.ino.bin
```

Arduino IDE 中选择 `unihiker k10` 后可编译。若 Windows 用户名包含中文且旧版 K10 GCC 报 `CreateProcess: No such file or directory`，应从纯 ASCII 路径调用同一工具链；这属于旧工具链路径解析问题，不是程序语法错误。上传前必须重新确认实际串口。

## 10. 真机检查步骤

1. 断电完成 K10、L298N、电机和独立电机电源接线，确认共地和 ENA/ENB 跳帽。
2. 暂时架空车轮，填写 Wi-Fi 后上传。
3. 确认方向 1 的实际画布为 320×240：启动时电机停止，STARTUP、WAITING 均无裁切，文字不倒置；原机身上边缘和 USB 出线位于阅读者右侧。
4. 查看串口中上海、台中各自的 HTTP 状态和 Parsed 行；不得出现密码。
5. 两地都成功后确认 NEW LETTER 的 From、To、天气摘要、信封、mood 和 MOVING 不重叠，并且只触发一次前后往复。
6. 进入 READING 后检查标题、城市方向、页码、8 行正文和温度/Wi-Fi 页脚；正文不得覆盖页脚，长城市名不得越界。
7. 等待自动翻页或按 Button B，确认无上一页残影且翻页不会再次触发电机。
8. 断开网络，确认横屏 ERROR/OFFLINE 页面完整、只显示简短错误，并可按 B 阅读缓存来信，电机保持停止。
9. 打开 `DEMO_MODE` 后按 Button A，验证缓存演示来信和一次电机通知。
10. 若车轮方向不一致，分别调整 `LEFT_MOTOR_REVERSED` 或 `RIGHT_MOTOR_REVERSED`。

## 11. 已知限制

- HTTPS 原型使用 `client.setInsecure()`，有超时但不验证服务器证书；
- 来信和两地天气只保存在 RAM，重启后重新请求；人格仍由 Preferences 持久化；
- HTTP GET 是有限超时的同步操作，请求期间电机被强制停止；
- 中文 UTF-8 边界已在代码中安全处理，但字体显示效果尚未经过实体 K10 验证；
- 编译成功不能替代 Wi-Fi、屏幕、电机方向、电源抗干扰等真机测试。
